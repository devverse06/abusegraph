# AbuseGraph

**Razorpay AI Buildathon 2026 | Track 02: AI Risk Manager**

AbuseGraph is a defense-only abuse-ring sentinel. It surfaces coordinated customer activity that may look ordinary when each account is examined alone, using shared infrastructure and transaction/loss signals as investigation evidence.

## Problem statement

Abuse rings can reuse devices, payment instruments, and addresses across multiple customer accounts while distributing refunds, chargebacks, and other losses across individually ordinary activity. A behavior-only customer score can miss that coordination.

AbuseGraph is designed to help a risk analyst find those relationships without automatically blocking or punishing customers.

## Solution

The system combines an explainable customer relationship graph with deterministic behavioral and loss signals. It identifies connected components that share at least two independent resource types, scores the components and their members, and produces an evidence bundle for manual investigation.

Ground-truth labels are used only for evaluation and threshold selection. They are not detector features.

## Architecture

```text
synthetic customers, transactions, outcomes, and resource links
                         |
                         v
       customer features + explainable relationship graph
                         |
                         v
          AbuseGraph component and member risk scores
                         |
                         v
              compact evidence bundle for investigation
                         |
              optional structured LLM investigation
                         |
                  evidence verifier
                    /          \
             verified output   deterministic fallback
                    \          /
                    manual investigation only
```

The project contains synthetic data generators, the graph detector and behavior baseline, evaluation code, AI contract/adapter/verifier/fallback modules, generated artifacts, and a browser demo.

## Synthetic dataset

The deterministic generator produces:

- 10,000 customers
- 80,000 transactions
- 139 abuse rings
- 500 `ABUSE_RING` customers
- 100 `MIXED` customers with both normal and abusive transactions
- legitimate shared-resource customers for false-positive testing
- four abuse archetypes: burst, slow-burn, amount-pattern, and behavioral-similarity

Generated CSV files include customers, transactions, refunds, chargebacks, rings, devices, addresses, payment instruments, and customer-resource links.

## Detection methodology

**The behavior baseline uses per-customer refund rate (55%), chargeback rate (35%), and transaction activity (10%). It computes median transaction amount but does not include it in the baseline risk score.**

AbuseGraph adds:

- customer edges from shared devices, addresses, and payment instruments
- a requirement for at least two independent shared-resource signals per edge
- connected-component network evidence
- refund and chargeback behavior
- same-hour temporal coordination
- behavioral similarity
- amount-pattern evidence
- member-level risk scores and `HIGH`, `REVIEW`, or `LOW` risk bands

The detector is deterministic and explainable. It does not use a graph neural network or automatic enforcement.

## Evaluation methodology

The benchmark is generated by `run_pipeline.py` with the current deterministic seed.

- Transactions are split chronologically into 70% train, 15% validation, and 15% held-out test.
- The threshold is selected on the validation period using F1, with precision as the tie-breaker.
- At each cutoff, the detector may use unlabeled events and resources observed through that cutoff.
- The protocol is cumulative **post-event batch investigation**: accumulated refund and chargeback outcomes may be available to the detector.
- Final metrics are reported on the held-out test period only.
- Customer labels are evaluation-only and are not detector features.

This is a held-out batch evaluation, not a real-time pre-refund or pre-chargeback prediction benchmark.

## Business impact

On this synthetic holdout, AbuseGraph reduces false positives from 80 to 66 and the modeled operational cost from ₹6,000.00 to ₹4,950.00. Missed abuse exposure falls from ₹2,95,225.36 to ₹87,468.52, a reduction of ₹2,07,756.84. Ring recall is 92.09% when a ring counts as found at 50% member coverage.

The cost model uses a fixed ₹75 operational cost per false-positive customer. Exposure is the transaction amount associated with missed abusive customers in the evaluated batch.

## AI investigation

The detector creates a compact case containing cluster risk, account count, shared-resource counts, loss rates, coordination, behavior similarity, potential exposure, and member risk bands.

The optional server-side Gemini adapter receives that case and requests structured JSON containing:

- summary and risk assessment
- key findings and counter-evidence
- uncertainty
- recommended action
- priority members

Gemini is optional. The browser never receives an API key, and the investigation remains usable through the deterministic fallback when no provider is configured or a provider call fails.

## Evidence verifier and hallucination rejection

Before a model response reaches the UI, the verifier checks the allowed risk and action values, evidence-path allowlisting, and that priority member IDs exist in the supplied case. Unsupported evidence paths, invalid actions, malformed output, and hallucinated customer IDs are rejected.

The demo's **Inject hallucination** control supplies `C_HALLUCINATED`; the verifier rejects it and the pipeline returns the deterministic fallback. Recommended actions are limited to `NO_ACTION`, `MANUAL_REVIEW`, and `PRIORITY_REVIEW`. No automatic blocking or punishment is available.

## Deterministic fallback

The fallback investigator uses only the case evidence, produces an evidence-grounded investigation narrative, includes counter-evidence and uncertainty, and recommends manual investigation where appropriate. It requires no Gemini credentials or external service.

## API endpoints

The minimal local server is implemented in `demo/server.py`:

- `GET /api/health` returns application, detector, verifier, and synthetic-dataset status.
- `POST /api/investigate` runs the optional provider or deterministic fallback.
- `POST /api/investigate?mode=hallucinate` exercises verifier rejection and fallback recovery.

Investigation requests do not accept a request body. Unsupported query parameters, invalid modes, and bodies receive a generic 400 response. Unexpected server failures are logged server-side and return only a generic 500 response.

## Run locally

From the project root:

```bash
python -m pip install -r requirements.txt
python generate.py
python run_pipeline.py
python -m pytest -q
python demo/server.py
```

Open `http://127.0.0.1:8000/demo/`.

### Optional Gemini provider

Set `GEMINI_API_KEY` and optionally `GEMINI_MODEL` in the server environment. Do not commit `.env` or API keys. The checked-in `.env.example` contains only a placeholder. Without credentials, the deterministic fallback is the expected working mode.

## Security and deployment notes

- Static serving is allowlisted to `/demo/`, `/demo/index.html`, `/generated_case.json`, and `/artifacts/evaluation.json`.
- Source files, `.git`, `.env`, credentials, private configuration, output CSVs, and arbitrary paths are rejected.
- `.env` is ignored by Git and no live `.env` file is required for the fallback.
- Client errors do not expose stack traces, exception internals, API keys, or file paths.
- The local demo server has no authentication or rate limiting and should not be exposed directly to the public internet without deployment-level access controls.
- This prototype does not process real payments or move real money.

## Known limitations

- The dataset is synthetic and intentionally constructed to test engineering trade-offs.
- The benchmark is cumulative post-event batch investigation, not online pre-outcome prediction.
- Shared resources can be legitimate, stolen, recycled, or dynamically changing in real systems.
- The benchmark uses a fixed deterministic corpus and seed; it does not provide multi-seed confidence intervals.
- The verifier constrains structure, evidence paths, allowed actions, and customer IDs, but is not a complete semantic fact-checker for every natural-language claim.
- Production use would require richer telemetry, calibrated costs, policy controls, monitoring, governance, access control, and human review.
